# 已知问题

按发现顺序记录，未修复的留在原处。每条都带**复现方式**与**当前行为**，不写猜测的根因。

## 1. 系统提示词没告诉模型「写入记忆是网关自动做的」

**发现于** 2026-09-10 本机 E2E（docker Postgres + DeepSeek）。

**复现**

```bash
curl -s http://127.0.0.1:4100/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"remember-dev","messages":[{"role":"user","content":"请记住：我的幸运数字是 7788。"}]}'
```

**当前行为** 模型回复：

> 我没法写入长期记忆——当前可用的工具只有 recall_memories（只读检索），没有保存记忆的接口。所以「记住了」这个回复我给不了实话……

**问题** 写入是网关自动归档的（用户不需要、也没法手动触发）。但系统提示词只给了只读的 `recall_memories` 工具、没说清写入是隐式发生的，模型据此推断「我做不到」，于是向用户道歉并给出「建议你手动记进长期记忆」这种做不到的建议。

**影响** 用户第一次让 AI 记东西就会撞上，且这句话直接否定了产品价值。

**待定** 修 prompt（在系统提示里说明归档是自动的）还是把写入也做成工具。别急着定。

## 2. 记忆把元指令原样存下来，下一轮复述给用户

**发现于** 同一次 E2E，紧接着 #1。

**复现** 先发「请记住：我的幸运数字是 7788。**只回「记住了」三个字。**」，再独立发一轮「我的幸运数字是多少？」

**当前行为** 第二轮答对了 7788，但附带：

> （补充说明：记忆里这条还附带了「只回『记住了』三个字」的要求，那是当初你让我记下它时的回复格式约定，跟现在这个问题无关，所以我按你现在的提问正常回答了。）

**问题** 存进去的是用户整句原话，没有把「事实」（幸运数字=7788）与「指令」（只回三个字）分开。调用方给模型的输出格式约束泄漏成了长期记忆内容。

**影响** 记忆库被格式指令污染，检索回来的噪音会挤占上下文（该轮 prompt_tokens 从 489 涨到 1143）。

## 3. 模型目录快照滞后于上游，告警措辞指向用户

**发现于** 同一次 E2E。

**现状**

| 来源 | deepseek 的模型 id |
|---|---|
| models.dev 快照（`@opencode-ai/models`，离线目录） | `deepseek-v4-flash`、`deepseek-v4-flash-vision-exp`、`deepseek-v4-pro` |
| DeepSeek `GET /models`（线上实时） | `deepseek-flash`、`deepseek-v4-pro` |

**注意** 三个信号里有两个会误导，只有实测算数：

- `GET /chat/completions` **别名照收**：传 `deepseek-v4-flash` 返回 200，响应里 `model` 被归一化成 `deepseek-flash`（`deepseek-flash` / `deepseek-v4-pro` 同样 200）。
- 传一个真不存在的 id 时，上游的报错文案是「The supported API model names are **deepseek-flash, deepseek-v4-pro**」——**它只列规范名，不提别名**。拿这句话当权威清单会把有效 id 判成无效。

所以「id 是否有效」只能靠发一次请求判，不能靠 `/models` 列表、也不能靠上游报错文案。

**当前行为** 用户填 `--model deepseek-flash`（**上游自己公布的 id**）时：

```
▲  「deepseek」的目录里没有模型「deepseek-flash」，仍然按你给的名字用
```

**问题** 这是**目录滞后**，不是用户填错。措辞是「你没填对」，方向反了。

**影响** 不至于失败（`resolveTarget` 只 warn 不拦，这是对的），但会让用户反复核对自己抄没抄错。

## 4. `init --host` 是死 flag

**位置** `apps/cli/src/flags.ts` 解析 `--host` 并写入 `InitOptions.host`，`apps/cli/src/init.ts` 的函数体从未读过它。

**影响** 无功能影响（无人值守若只给 `--host` 会走不到预期分支，但 `assertUnattendedReady` 也不认它）。属于该删或该接上二选一。

## 5. 重跑时 postgres 的原始 NOTICE 糊到控制台

**发现于** 同一次 E2E，第二次 `init --yes`（幂等重跑）。

**当前行为**

```
┌  remember-api 本地部署向导
│
  severity_local: 'NOTICE',
  severity: 'NOTICE',
  code: '42P06',
  message: 'schema "drizzle" already exists, skipping',
  file: 'schemacmds.c',
  ...
```

**根因** `packages/db/src/migrate-core.ts:22` 的 `createClient(url, { max: 1 })` 没传 `onnotice`；`client.ts:50` 只在传了的时候才挂抑制器，否则 postgres-js 用默认处理器把通知打到 stdout。对照 `apps/cli/src/db.ts` 的 `oneShot`，那里是显式传了 `onnotice: () => {}` 的。

**为什么只在重跑时出现** 首次是 `CREATE SCHEMA`（无 IF NOT EXISTS 冲突）；重跑走的是 `IF NOT EXISTS` 且对象已存在 → 触发 42P06 / 42P07 通知。

**影响** 纯噪音，但**恰好落在「Ctrl-C 后重跑」这条产品明确承诺干净的路径上**，而且它是 JSON 对象 dump，用户会以为自己哪里配错了。

**修法** `runMigrations` 加 `onnotice: () => {}`（或接一个 `log` 参数转成 spin.message）。注意别把**真实错误**一起吞了——`onnotice` 只挡通知，错误仍走异常。

## 6. `status` 报不出「有没有实例在跑」，`up --port` 也不落盘

**严重度** 低，但属诊断缺口。

**现状** `up --port 4100` 只改本次运行，不写回 `config.server.port`。于是：

- 网关实际跑在 4100；
- `status` 报的是配置里的 4000，并显示「端口 4000 空闲」，又在同一屏说「容器 remember-pg: running」。

「空闲」在这里的语义是「这个端口没人占」，读起来却像「没有实例在跑」。CLI 全命令没有任何一个能回答「现在有没有 remember-api 在跑、跑在哪个端口」。

**为什么算问题** 这个产品的立身之本是「你用 CLI 就能管住全部，不用去翻 .env 和进程」。用户 `up` 完之后开新终端想确认状态，只能得到误导性的「空闲」。

**待定** 是让 `--port` 落盘，还是让 `status` 主动扫一遍本机监听（例如探测配置端口 + 常见端口），还是把「运行中」做成 pidfile / 健康探测。别急着选。

## 7. 对同一个库重跑时，把我们自己的桩说成「原函数（未覆盖）」

**发现于** 2026-09-10，中断后重跑的恢复测试。

**复现** 对**自己刚建好的**库再跑一次 `init`：

```bash
node dist/cli.js init --yes --url postgres://postgres:postgres@127.0.0.1:5433/kill10 --provider deepseek --model deepseek-flash
```

**当前行为**

```
auth.uid() 已存在，沿用原函数（未覆盖）
```

**问题** 库里那个 `auth.uid()` **就是我们自己上一轮建的桩**（`SELECT null::uuid`）。措辞读起来像撞见了一个外来的真函数、于是谨慎地不碰它——但这是**每一次重跑**都会出现的常态，不是异常。

**根因** `apps/cli/src/db.ts` 的 `ensureAuthStub` 把两种情况合并成同一个 `"kept"`：

- 「已经是我们自己的桩」→ 重跑常态，应该平静地说「桩已就位」；
- 「是别人的真函数」→ 这次真的需要**大声说**，因为它决定了 P0 那个安全 bug 是否被触发。

而 `isOwnAuthStub`（`db.ts:252`）已经写好、能区分这两者，**却只被它自己的测试文件引用**，生产路径从未调用（`prosrc` 在 `ensureAuthStub` 里本来就已经读到手了）。

**影响** 不丢数据、不影响正确性。但把「无事发生」渲染成「发现异常，已谨慎处理」，会让用户每次重跑都以为环境里混进了别的东西。对一个要打消「我是不是动坏了什么」疑虑的产品，这是反效果。

**修法** 返回三态 `"created" | "kept-ours" | "kept-foreign"`，日志分开说；`kept-foreign` 那支顺带把「这是 Supabase 自己的函数，RLS 归它管」讲明白。`isOwnAuthStub` 由此从死代码变成承重的一环。

**探针 1 第一次红得理由不对，值得记一笔**：它先是被 `TypeError: No "isCancel" export is defined on the mock` 掀翻的，不是被我要证的那条断言。原因是 `init.test.ts` 的 `@clack/prompts` mock 漏了 `isCancel`，而 `./prompt.js` 的 `unwrap` 要用它。把 `isCancel` 换成真货（`importOriginal`）后重探，才死在真正的那条断言上。**这个洞本身是个坑**：真 `isCancel` 就是 `e === CANCEL_SYMBOL`，自己造个 Symbol 传进去永远 false —— 假谓词会让「取消被当成正常值继续往下走」那条分支永远绿。

### 两条纠正过来的事实

| 流传的说法 | 实情 |
|---|---|
| dist 是单文件 | **不是**。动态 `import()` 触发 esbuild code splitting：`cli.js` + `chunk-*.js`×3 + `app-*` + `server-*` + `src-*`。`files: ["dist", …]` 收整个目录，tarball 完整（24 文件 / 957.6 kB 打包 / 7.6 MB 解包） |
| `init --port` 能指定容器名 | **不能**。`DEFAULT_DB_PLAN.container` 写死 `remember-pg`，所以 `ensureContainer` 的「创建」分支**只有第一次能跑到**，之后永远走「复用」。想换容器名目前只能改源码 |

### 明确没覆盖的

- **不打真 LLM**（只验到 `/v1/models`）。代价说清楚：真实厂商的 wire 契约、真实 `usage`、真实错误码**不在覆盖内**。上一节记的「真上游 802ms / 带真实 usage」那类证据，本 E2E 拿不到 —— 那仍然得手工打一次真 Key。脚本里 `POST /v1/chat/completions` 会**打印原因后跳过**，不会假装验过。
- **交互向导不测**：本机驱动不了 pty（见上一节）。`--yes` 是脚本/agent 的唯一入口，也是本次重点。
- **`model add` 不测**：它只有交互模式，非 TTY 下直接抛 `NeedsInteractiveError`。

### `next build` 会崩在 webpack 的缓存快照上，删 `.next` 即可

**发现于** 2026-09-11 改完 install 文档后跑全量验证。

**当前行为**

```
[MDX] generated files in 1016.6ms
Creating an optimized production build ...
uncaughtException [TypeError: Cannot read properties of undefined (reading 'length')]
```

Next 不给栈。用 `process.emit` 钩 `uncaughtException` 才看到真位置：

```
at WasmHash._updateWithBuffer        (next/dist/compiled/webpack/bundle5.js)
at <webpack FileSystemInfo._resolveContextTsh>
```

**不是文档改坏了**（这条最容易误判）：崩溃发生在 webpack 的**文件系统缓存快照**阶段，早于任何页面渲染。

**复现** 留下一个陈旧的 `.next/cache`（本例是 Sep 10 那份，且当时没有 `BUILD_ID`，即从未有过一次完整的产线构建），再跑 `next build`——连跑 4 次都是同一处崩，因为没有人删 `.next`。

**修法**

```bash
rm -rf apps/web/.next
pnpm --dir D:/coding/remember-api --filter @remember/web build
```

冷启动即过（实测 `✓ Compiled successfully` / `Generating static pages (31/31)` / 退出码 0）。**会复发**：只要 `.next/cache` 再次陈旧就可能重现，恢复手段同上。

**顺带一条真实的脆弱点**（本次未触发，仅记录）：`apps/web/node_modules/<pkg>` 在 Windows 上是 NTFS junction，`readlinkSync` 返回**绝对路径**；webpack 里那句 `path.join(dir, target)` 遇到绝对 target 不会重置，于是拼出
`apps\web\node_modules\D:\coding\...\node_modules\next` 这种不存在的路径 → readdir 失败 → 子哈希 `undefined` → 就是上面那个 `length` 崩溃处。Linux/macOS 上 pnpm 用相对符号链接，所以这是 Windows 特有的。**它只是同一条代码路径上的隐患，不是本次的触发原因。**

## Supabase 云端路径（2026-09-11）

上一节那张表里 Supabase 记的是「需云凭据，本机跑不了」。这轮把它变成了脚本，同时挖出一个**真缺陷**，和两条**记错的网络事实**。

### 挖出的真缺陷：`init --url <事务池串>` 会让 DDL 跑在 pgbouncer 上

链路三处接力，没有一处单独看是错的：

| 位置 | 行为 |
|---|---|
| `apps/cli/src/init.ts` 的 `--url` 分支 | **永远**写 `migrateUrl: null` |
| `apps/cli/src/config.ts` | 只有 `migrateUrl` 非空才设 `MIGRATE_DATABASE_URL` |
| `packages/db/src/migrate.ts` | 没设就**回退 `DATABASE_URL`** —— 用的正是那条事务池串 |

文档专门用 Callout 警告「两条串不能混用，DDL 走池化端口会失败」，CLI 自己却违反了。**这也解释了这条路径为什么从没被端到端验证过：它本来就走不通。** 修法是 `db.ts:resolveMigrateUrl`：池化串 → 同 host 换 5432；直连域名 → 直接报错并给出池化替身（它有 IPv6-only 的坑）；其余 → 一条串够用。

### 记错的两条网络事实

| 之前的记录 | 实情 |
|---|---|
| 「Supabase 直连/pooler 在当前网络**不可达**」 | 池化地址**是通的**，认证也过。不可用的是**直连域名** `db.<ref>.supabase.co` —— 只解析出 IPv6、无 A 记录，纯 IPv4 网络里 DNS 直接失败 |
| 「区域 us-west-2」 | **us-east-1**（注释里的区域写错了，`.env` 已更正） |

### 还卡着的一处：池化**端口**出口被挡

不是凭据问题，也不是代码问题，是这台机器到 `*.pooler.supabase.com:5432/6543` 的 TLS 握手**收不到一个字节**（TCP 能建连）。跨区域（us-east-1 / us-west-1 / ap-southeast-1）、跨 IP（三条 A 记录全试）、跨重试（8/8 失败）表现一致；**Docker 里也一样**（`psql: SSL error: unexpected eof while reading`），所以容器绕不过去。同主机的 443 部分可达（`api.supabase.com:443` 正常）。

脚本把这条做成了**显式前置探针**：TCP 通、TLS 不通时直接报这个结论，而不是让人去查密码。**所以本机 `node scripts/install-e2e.mjs supabase` 是红的，且红得正确**；换一个 TLS 能握上手的网络即可跑绿。

### 跑法

```bash
node scripts/install-e2e.mjs supabase   # 需云凭据
node scripts/install-e2e.mjs all        # local + npx（**故意不含云端**，那两条不需要外网）
```

凭据优先读 env，回退**只读** `apps/api/.env`（变量：`E2E_SUPABASE_DB_URL` / `E2E_SUPABASE_MIGRATE_URL` / `E2E_SUPABASE_URL` / `E2E_SUPABASE_SERVICE_ROLE_KEY` / `E2E_SUPABASE_ANON_KEY`）。读取时**不回写 `process.env`**，否则 local/npx 两条路会沾上云端凭据。日志里连接串只打印 `user@host`，不打印密码。

`E2E_SUPABASE_CLI=1` 才会额外跑一次 `npx supabase` 的区域交叉核对，否则记 `⊘ 跳过`。

### 覆盖到了什么

| 断言 | 为什么值得单独存在 |
|---|---|
| 前置：凭据形状 + 出口可达性 | 把「网络不通」和「密码错」分开，这两种完全不同的结论在报错里长得一样 |
| 基线快照 → 清理后核对 | 唯一能证明清理真的干净的东西（见下） |
| `init` 打真云端，跑完 `auth.uid()` **逐字节比对** | P0：`ensureAuthStub` 若覆盖了真 `auth.uid()`，等于静默关掉 RLS。这条同时是「`migrateUrl` 推导」那个缺陷的变异探针 —— 迁移步走的就是 CLI 自己推的串 |
| `/api` 四种非法凭证必须 401 | 不带 token、拿 `rma_` key 当 Bearer、**签名伪造但 iss/aud/sub 全对**的 JWT、GoTrue 真登录后 200 |
| 网关**故意不注入** `DATABASE_SSL_CA` | 逼它走 `apps/api/certs/` 那份拷贝 —— 那正是 2b 修的构建缺口，不这样测就等于没测 |

`/api` 这一段是本地路没有的：`SUPABASE_URL` 为空时 `app.ts` 根本不注册 `managerRoutes`，请求会得到 404（不是 401）。所以 404 与 401 是两条不同的结论，脚本分开断言。

### 清理策略

`cleanups` 是 LIFO，**失败路径同样执行**：按外键序删种子行 → Admin API 删一次性 auth 用户 → 删 `init` 自己播下的用户（对基线做差集） → 停网关。

一行来之不易的规矩：**「清理后核对」必须注册在最前面**（LIFO → 最后执行）。注册早了就是在核对「还没清干净」的中间态，必然假红。另外它支持返回 `{ skipped }` —— 前面就中断时打 `⊘ 跳过` 而不是绿勾。**「没验成」和「验过了」在报告里长得一模一样，这正是假绿的来源**（这条是本轮自己踩出来的：第一版在基线没取到时打印了 ✓）。

### 明确没覆盖 / 没做

- **没跑成**：本机网络挡着（见上），所以「云端全绿」这句话**没有证据**。已验的是**失败路径红得准确**（`all` 两条本地路 22 绿 + 2 个合法跳过，退出码 0；`supabase` 给出上面那段诊断，退出码 1）。
- **前置导出没做成**：迁移前要把云端现存的 `public.users` / `public.api_keys` 各 1 行导出留底，同样卡在这条网络上，**没有执行**。诚实说明它的边界：迁移 `0003` 会给 `api_keys.profile_id` 加 NOT NULL + 外键，所以那份导出是**记录**，不是一键回滚的备份。
- **不打真上游 LLM**（沿用既有选择）。
- **私人服务器路径**仍需 VPS。

### 文档与 CLI 双轨：云端拆成「Supabase / 自定义」

- **CLI**：`init` 走到「没有 Docker」时不再直接要串，而是先问云端两条路哪一条。选 Supabase 会调 `npx supabase projects list` 列出项目 → 让你贴一次 Dashboard 的池化串 → **校验**它（区域 / ref / 端口）→ 自动推出 5432 那条。**CLI 不可用、没登录、输出解析失败都不挡路**：说明原因后退回手填。校验逻辑在 `apps/cli/src/supabase.ts`，14 条单测。
  - 主机名里那一段（`aws-0-` / `aws-1-`）**推不出来** —— 同区域两种前缀都真实存在，所以宁可让人贴一次，也不猜一个可能错的值。
- **文档**：`install/cloud-db.mdx`（zh + en，当时还叫 `install-supabase.mdx`）第 3 步拆成 Tabs 两栏；`install/cloud-server.mdx`（当时叫 `install-server.mdx`）里那条写错的 `MIGRATE_DATABASE_URL=<Supabase 直连串，5432>` 已更正为同池化主机的 5432；`install/local.mdx` 的 npx 栏（当时是独立的 `install-cli.mdx`）补了两条云路径与 `--migrate-url`。

### 变异探针（本轮）

逐条改坏 → 确认红 → 改回。**跑得动的两条都真跑了，跑不动的如实标出来**。

| 改坏什么 | 期望 | 实际 |
|---|---|---|
| `resolveMigrateUrl` 不换端口（复现修复前那个缺陷） | 迁移串推导的断言红 | ✅ 红在**两处独立断言**：`db.test.ts:91`（纯函数）与 `init.test.ts:364`（推导出的值确实传到了 `prepareDatabase`）。只算不传的实现能过前者、过不了后者。还原后复跑 **71/71 绿** |
| 打断 `apps/api` 构建的拷贝（`build` 只留 `tsup`）并删掉 `apps/api/certs/` | 新增的「产物自带根 CA」断言红 | ✅ 红在预期的 **`构建网关产物`** 步（前三步照常绿），消息是 `产物里没有 …/apps/api/certs/supabase-ca.pem` |
| E2E 清理漏删一张表 | 清理后基线核对红 | ❌ **未跑** —— 在云端路径里，本机网络到不了 |

那条 CA 探针能跑，是因为它被接在 `runLocal` 的构建步上（不只是云端路径）：本地路不握手 TLS，但「产物是否自带 certs」的道理一样，接上去就让它在这台机器上可验证。

**一处没说满的天花板**：该探针删的是整个 `apps/api/certs/`，所以只走到 `existsSync` 那一支；「文件在、但内容与源码树不一致」的 `Buffer.equals` 分支**没有被探到**。

**还原的证据**（探针改的是源码与产物）：`apps/api/package.json` 改前改后 md5 相同（`218b1f8f…`，`build` 行恢复成 `tsup && node scripts/copy-assets.mjs`）、`apps/api/certs/supabase-ca.pem` 与源码树 `cmp -s` 逐字节相同、无 `e2e_*` 孤儿库、仓库内无游离文件。临时文件都在 `os.tmpdir()` 下。
