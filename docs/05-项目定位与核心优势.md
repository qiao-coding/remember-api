# 05 · remember-api 项目定位与核心优势

> 快照日期：2026-09-08
>
> 采集性质：产品战略定位陈述（顶层「我们是谁」），区别于 `04-项目价值评估.md`（价值判断）。供产品方向对齐、对外介绍、PRD 上游引用。

## 1. 一句话定位

**Remember API 是一个属于用户自己的 Personal AI Gateway，让用户的记忆、偏好、项目上下文和 AI 身份独立于任何模型厂商，并可以自由调用和切换不同的大模型。**

> **模型可以换，但"你的 AI"不需要重来。**

---

## 2. 我们正在解决什么问题

今天用户使用 AI 时，真正被绑定的已经不只是模型，而是整个 AI 使用历史。

例如一个用户长期使用 ChatGPT 后，ChatGPT 可能已经逐渐了解：

- 用户是谁
- 用户正在做什么项目
- 用户喜欢什么技术栈
- 用户的表达方式
- 用户长期目标
- 用户过去做过的决定
- 用户的工作习惯
- 用户希望 AI 如何回答问题

但这些信息通常存在于特定产品内部。

于是出现一个明显的问题：

```text
ChatGPT 中的我
≠
Claude 中的我
≠
Cursor 中的我
≠
其他 Agent 中的我
```

每更换一个 AI 产品，用户就需要重新：

- 描述自己
- 描述项目
- 配置 Prompt
- 导入上下文
- 建立 AI 使用习惯

模型越来越强，但用户自己的 AI 上下文仍然被分散在不同厂商之间。

---

## 3. Remember API 的核心思想

Remember API 希望把这套关系反过来。

传统模式：

```text
用户
 ↓
ChatGPT / Claude / Cursor
 ↓
厂商自己的 Memory
 ↓
厂商自己的模型
```

Remember API：

```text
                     用户

                      ↓

               Personal AI
               Remember API

        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     Memory        Identity       Agents
        │             │             │
        └─────────────┼─────────────┘
                      ↓
                 Model Router
                      ↓
        ┌─────────────┼──────────────┐
        ↓             ↓              ↓
      GPT          Claude        DeepSeek
                                     ↓
                          Gemini / Qwen / Local LLM
```

用户首先调用的不是某一个模型。

而是：

> **"我的 AI"。**

然后由 Personal AI 根据任务选择或调用底层模型。

---

## 4. 核心理念

### 用户拥有 AI，模型只是算力供应商

Remember API 最重要的设计原则是：

> **Identity belongs to the user.**
> **Memory belongs to the user.**
> **Models are replaceable.**

用户真正拥有的是：

```text
Personal AI
├── Identity
├── Memory
├── Preferences
├── Projects
├── Instructions
├── Agent State
└── Permissions
```

模型则只是：

```text
Providers
├── OpenAI
├── Anthropic
├── Google
├── DeepSeek
├── Qwen
└── Local Models
```

这意味着：

如果今天使用 Claude：

```text
Personal AI
    ↓
Claude
```

明天 Claude API 不再可用：

```text
Personal AI
    ↓
GPT / DeepSeek / Gemini / Qwen
```

用户的记忆、身份和长期上下文依然存在。

---

## 5. Remember API 不是什么

### 不是另一个 ChatGPT

Remember API 不打算重新制造一个聊天应用。

聊天 UI 可以有很多个。

Remember API 希望成为聊天应用背后的个人 AI 层。

---

### 不是单纯的 RAG

RAG 解决的是：

> "如何找到相关资料？"

Remember API 解决的是：

> "这个 AI 为什么知道我是我？"

例如：

```text
知识：
React 19 有哪些 API？

记忆：
这个用户更喜欢 React，
目前正在开发一个 TypeScript 项目，
并且希望避免过度复杂的架构。
```

两者不是一个问题。

---

### 不是单纯的 Memory SDK

传统 Memory SDK 通常解决：

```text
开发者的 AI App
        ↓
     Memory
```

Remember API 希望解决：

```text
                用户
                 ↓
            Personal AI
                 ↓
        ┌────────┼────────┐
        ↓        ↓        ↓
      App A    App B    App C
```

Memory 不再天然属于某一个应用。

而属于用户。

---

## 6. 核心优势

### 6.1 模型无关

Remember API 不要求用户绑定某一家模型厂商。

同一个 Personal AI 可以：

```text
写代码 → Claude

普通聊天 → DeepSeek

复杂推理 → GPT

长文本 → Gemini

隐私任务 → Local Model
```

模型可以根据：

- 能力
- 成本
- 延迟
- 上下文长度
- 可用性

动态选择。

---

### 6.2 避免 Vendor Lock-in

如果整个 AI 身份都存在某个平台：

```text
账号
+
Memory
+
Conversation
+
Agent
+
Model
```

迁移成本会越来越高。

Remember API 将这些拆开：

```text
用户资产
────────────
Identity
Memory
Preferences
Projects
Agent State

模型服务
────────────
OpenAI
Claude
DeepSeek
Gemini
...
```

模型提供商可以替换。

用户资产不需要迁移。

---

### 6.3 跨 AI 工具共享上下文

未来一个用户可能同时使用：

```text
Chat App
IDE Agent
Browser Agent
Writing Agent
Game Agent
Voice Assistant
```

这些工具理论上都可以访问同一个经过授权的 Personal AI。

于是：

```text
IDE 中知道的项目
        ↓
聊天 AI 也知道

聊天中做出的决定
        ↓
Agent 也可以继续执行
```

减少重复解释上下文。

---

### 6.4 用户数据主权

Remember API 的长期目标不是：

> "我们替用户拥有这些数据。"

而应该是：

> **用户拥有自己的 AI 数据。**

包括：

- 可查看
- 可修改
- 可删除
- 可导出
- 可备份
- 可迁移

未来甚至可以支持：

```text
Self-hosted Remember API
```

让用户真正拥有自己的 Personal AI Backend。

---

### 6.5 Personal AI ID

Remember API 最终可以不仅仅是一套 Memory API。

而形成：

```text
Personal AI Identity
```

类似今天：

```text
手机号
Email
GitHub Account
Apple ID
```

未来可能出现：

```text
Personal AI ID
```

用户可以使用同一个 AI Identity 登录不同 AI 应用。

应用不需要从零认识用户。

---

## 7. 一个典型使用场景

假设用户告诉 Personal AI：

> 我是一名前端开发者，目前主要使用 TypeScript 和 React。我喜欢简单直接的架构，不希望为了抽象而抽象。

Remember API 保存：

```json
{
  "preferences": {
    "language": "TypeScript",
    "frontend": "React",
    "architecture": "prefer-simple"
  }
}
```

用户首先通过 GPT 工作。

```text
User
 ↓
Remember API
 ↓
GPT
```

一个月以后切换 Claude：

```text
User
 ↓
Remember API
 ↓
Claude
```

Claude 仍然可以知道：

```text
用户偏好 TypeScript
用户使用 React
用户偏好简单架构
用户当前项目背景
```

不需要重新建立关系。

---

## 8. 更进一步：Agent 状态也属于用户

Memory 只是第一步。

未来 Remember API 可以进一步保存：

```text
Agent State
```

例如：

```json
{
  "project": "remember-api",
  "goal": "build MVP",
  "completed": [
    "memory storage",
    "provider adapter"
  ],
  "next": [
    "model router",
    "authentication"
  ]
}
```

那么即使：

```text
昨天：Claude 完成任务

今天：GPT 接手

明天：Local Agent 继续
```

任务仍然可以持续。

这意味着：

> **AI 工作流不再属于模型 session，而属于用户。**

---

## 9. MVP 定位

第一版不需要解决所有 Personal AI 问题。

MVP 只验证三个能力。

### Memory

```text
POST /memory

GET /memory

DELETE /memory
```

允许 Personal AI 保存和检索用户长期记忆。

---

### Model Gateway

提供统一入口：

```text
POST /chat
```

例如：

```json
{
  "model": "claude",
  "message": "帮我设计这个项目"
}
```

或者：

```json
{
  "model": "gpt",
  "message": "继续刚才的项目"
}
```

两个模型使用相同用户上下文。

---

### Provider Switching

支持至少：

```text
OpenAI
Anthropic
DeepSeek
```

Demo 最重要的一幕：

```text
GPT
 ↓
知道用户

切换

Claude
 ↓
仍然知道用户
```

这就是 MVP 最核心的产品价值展示。

---

## 10. MVP 暂时不需要做什么

第一阶段不要急着加入：

- 复杂 Multi-Agent
- AI OS
- Marketplace
- 完整 MCP 平台
- 社交系统
- 去中心化协议
- 极复杂知识图谱
- 自动 Agent 编排

这些都可以以后增加。

现在最重要的是验证：

> **"一个独立于模型厂商存在的 Personal AI，是否真的比单独使用模型更好？"**

---

## 11. 第一批目标用户

Remember API 的第一批用户不应该是普通消费者。

最适合的是：

### AI Heavy Users

同时使用：

```text
ChatGPT
Claude
Gemini
DeepSeek
```

的人。

---

### Developers

同时使用：

```text
Cursor
Claude Code
Codex
ChatGPT
IDE Agents
```

的人。

这些用户最容易感受到上下文割裂。

---

### Agent Developers

他们需要：

- 长期 Memory
- 用户 Profile
- Provider Router
- Persistent State

Remember API 可以直接成为他们的基础设施。

---

## 12. 产品护城河

Remember API 真正长期的价值并不只是：

```text
Vector Database
```

因为这部分很容易复制。

真正可能形成价值的是：

### Memory Governance

解决：

```text
什么应该记住？
什么应该忘记？
哪些 Memory 已经过时？
Memory 发生冲突怎么办？
不同 App 能访问哪些 Memory？
```

---

### AI Identity

建立统一的：

```text
User → Personal AI
```

身份关系。

---

### Permission System

例如：

```text
Coding Agent
→ 可以读取项目记忆

Shopping Agent
→ 可以读取消费偏好

Public App
→ 不能读取私人记忆
```

---

### Ecosystem

最终最理想的状态：

```text
任何 AI App
       ↓
Connect Remember
       ↓
立即获得用户授权的上下文
```

类似今天：

```text
Sign in with Google
```

未来可能变成：

```text
Connect your Personal AI
```

---

## 13. 与手机号 / SIM 卡的类比

Remember API 可以使用一个非常容易理解的类比：

过去：

```text
手机号属于用户

手机可以换

运营商可以换
```

未来：

```text
Personal AI 属于用户

AI App 可以换

模型厂商可以换
```

所以：

> **模型不是你的 AI。**

就像：

> 手机不是你的手机号。

模型只是运行 Personal AI 的其中一个计算资源。

---

## 14. 项目长期愿景

Remember API 最终希望成为：

> **The portable identity and memory layer for Personal AI.**

让用户拥有一个：

```text
长期存在
可迁移
跨模型
跨应用
可控制
可导出
```

的个人 AI。

今天：

```text
用户属于 AI 平台
```

希望未来变成：

```text
AI 平台接入用户的 Personal AI
```

---

## 15. 核心 Slogan

英文主 Slogan：

> **Your AI. Your Memory. Any Model.**

另一版：

> **Models change. Your AI remembers.**

强调产品定位可以使用：

> **The portable memory and identity layer for Personal AI.**

中文：

> **模型可以换，你的 AI 不需要重来。**

或者：

> **属于你的 AI，而不是属于某个模型厂商的 AI。**

---

## 16. 当前最重要的验证目标

Remember API 现在不需要证明自己能够成为未来 AI 标准。

第一阶段只需要回答：

> **如果一个用户可以在 GPT、Claude、DeepSeek 之间随意切换，同时保持同一个身份、记忆和上下文，他是否愿意持续使用这种方式？**

如果答案是 Yes，

那么 Remember API 才值得继续从：

```text
Memory API
```

发展为：

```text
Personal AI Gateway
        ↓
Personal AI Identity
        ↓
Personal AI Infrastructure
```

这也是项目最核心的演进路径。

---

## 17. 项目定位总结

Remember API 的竞争点不应该是：

> "我们拥有更好的向量数据库。"

也不是：

> "我们的 RAG 更快。"

真正应该强调的是：

> **Remember API 将 AI 的身份、记忆和长期状态从模型厂商中抽离出来，使用户第一次可以拥有一个真正可迁移、跨模型、跨应用的 Personal AI。**

最终目标不是让用户选择：

```text
我要使用哪一个 AI？
```

而是：

```text
这是我的 AI。

至于今天由哪个模型运行它，
并不重要。
```
