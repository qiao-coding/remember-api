# 04 · remember-api 项目价值评估

> 快照日期：2026-09-08
>
> 取材来源：根目录产品文档、`docs/01-需求与范围.md`、`docs/03-接口契约.md`、`packages/core/src/context-builder.ts`、`packages/core/src/memory-budget.ts`、`apps/api/src/services/chat.ts`、`apps/api/src/services/memory-write.ts`、`packages/db/src/schema.ts`。

## 1. 一句话判断

remember-api 的核心不是“一个带记忆的 API 网关”，而是：

> **个人 AI 的长期状态层。**

它把用户的偏好、项目状态、历史决策、失败尝试、Skills 和模型配置从某一个 AI 工具里抽离出来，再通过 OpenAI-compatible API 提供给 Claude Code、Codex、Cursor、DeepSeek Harness 等客户端。

更短的产品表达：

> **换工具，不换记忆。**

## 2. 为什么“个人 AI”是核心

现在的 AI 工具大多以会话、项目目录或单个产品为边界。用户真正需要长期延续的东西，却不是某个聊天窗口，而是自己的工作方式和项目上下文：

- 我偏好什么技术栈、代码风格、沟通方式；
- 某个项目为什么选择这套架构；
- 当前做到哪一步；
- 哪些方案已经失败过；
- 哪些上下文每次都值得带上；
- 哪些记忆已经过时，应该修改或删除。

这些信息如果锁在某一个 Harness 里，用户每换一个工具就要重新解释一次。remember-api 的价值在于让“个人上下文”成为独立资产：Harness 负责执行，模型负责生成，remember-api 负责保存和注入个人状态。

## 3. 项目当前已经具备的价值基础

### 3.1 Profile 把个人 AI 变成可选择的 model

接口层已经把 `model` 解释为 Profile 名。客户端仍然只发标准 OpenAI 请求：

```json
{
  "model": "remember-dev",
  "messages": []
}
```

但 remember-api 内部会解析出：

- 使用哪个 Provider；
- 对应哪个真实 base model；
- 是否启用 Memory；
- 绑定哪个 Project；
- 注入哪些 Skills；
- 使用多少 memory budget。

这让用户不需要等待客户端支持自定义记忆协议，只要能改 Base URL、API Key、Model，就能接入自己的个人 AI。

### 3.2 Context Builder 是产品心脏

`Context Builder` 已经把 Profile system prompt、User Preferences、Project、Relevant Memory、Skills 和原始 messages 组装成最终模型上下文，并记录各段 token 消耗。

这说明 remember-api 不是简单转发器。它真正做的是：

```text
用户请求
  ↓
识别个人 Profile
  ↓
取出用户偏好和项目上下文
  ↓
裁剪相关记忆和 Skills
  ↓
生成最终上下文
  ↓
交给底层模型
```

个人 AI 的“人格连续性”和“项目连续性”就在这一层发生。

### 3.3 Memory Budget 让记忆可控

记忆系统最大的风险是越用越贵、越用越乱。项目中已经有 `Memory Budget`，按 pinned、决策、问题、状态、任务、偏好、历史等优先级裁剪候选记忆。

这是一条很重要的产品路线：remember-api 不应该承诺“无限记忆”，而应该承诺“有边界、可观察、可编辑的高价值记忆”。

### 3.4 Memory Write 已有长期沉淀雏形

当前异步写入会识别用户偏好、架构决策、失败尝试、完成状态，并在写入前做相似检索去重。

这意味着它不只是“把聊天记录存起来”，而是在尝试提炼对未来有用的状态：

- 用户明确要求记住的偏好；
- 项目采用或放弃的技术决策；
- 已完成的开发状态；
- 失败方案和原因。

这些正是个人 AI 持续变聪明的材料。

### 3.5 Web 控制台是个人 AI 的控制平面

Web 端不应该抢 Harness 的工作，不做聊天框、不做 IDE。它的价值是让用户能控制自己的个人 AI：

- 看 AI 记住了什么；
- 修改错误记忆；
- 固定关键记忆；
- 配置不同 Profile；
- 管理 Project 上下文；
- 查看 memory token 开销；
- 生成 API Key 并接入任意客户端。

这比“后台管理页面”更具体：它是个人 AI 的记忆仪表盘。

## 4. 与普通产品的差异

### 4.1 不是聊天产品

聊天产品的中心是对话框。remember-api 的中心是个人上下文。

用户不会因为这里也能聊天而选择它；用户会因为 Claude Code、Codex、Cursor 都能共享同一套记忆而选择它。

### 4.2 不是向量数据库

向量数据库只回答“搜到什么”。remember-api 还要回答：

- 这些记忆属于哪个用户；
- 属于哪个项目；
- 是否应该进入这次请求；
- 进入多少 token；
- 成本是多少；
- 用户能不能修正它。

### 4.3 不是模型代理

模型代理通常解决 provider 切换、计费和路由。remember-api 的独特性是把 `Profile` 伪装成 OpenAI model，让任何兼容客户端都能拿到完整个人上下文。

### 4.4 不是团队知识库

当前定位更适合个人。团队知识库强调共享资料，remember-api 强调“我的 AI 知道我如何工作”。这也是第一版最应该守住的边界。

## 5. 目标用户与高频场景

### 5.1 独立开发者

痛点：

- 同时使用 Claude Code、Codex、Cursor、DeepSeek 等工具；
- 每个工具都不知道其他工具里发生了什么；
- 经常要重复解释项目架构、偏好、当前进度；
- 开启长上下文又担心 token 失控。

价值：

- 一个 Profile 对应一种工作模式；
- 一个 Project 保存长期上下文；
- AI 能记住偏好、架构决策、失败尝试；
- Dashboard 能看到记忆开销是否值得。

### 5.2 高频 AI 编程用户

痛点：

- Agent 每次接手都要重新读大量文件；
- 项目决策散在聊天记录里；
- 换工具后上下文断裂；
- 不知道记忆注入到底多花了多少 token。

价值：

- 让“已理解过的项目背景”复用；
- 把失败方案变成未来提示；
- 通过 memory budget 限制额外成本；
- 用 Usage 判断记忆 ROI。

### 5.3 个人知识工作者

痛点：

- 不同 AI 客户端里的偏好和工作习惯分裂；
- 长期任务需要持续上下文；
- 记忆错误时难以纠正。

价值：

- 建一个稳定的个人偏好层；
- 用 Project 隔离不同主题；
- 通过 Memory 页面手动整理长期事实。

## 6. 首页应该讲清楚的亮点

当前首页信息偏少，是因为它只讲了“OpenAI 兼容网关 + 记忆”，还没有把个人 AI 的价值链展开。首页应该让用户看到这几件事：

### 6.1 个人 AI 的核心承诺

主标题建议围绕：

> **让你的 AI 换工具也记得你。**

辅助表达：

> remember-api 把个人偏好、项目记忆、Skills 和模型配置做成一个 OpenAI-compatible API。Claude Code、Codex、Cursor 接入同一个 Base URL 后，就能共享同一套长期上下文。

### 6.2 三个一眼可懂的收益

1. **跨客户端连续**
   - 不管用 Claude Code、Codex 还是 Cursor，Profile 都指向同一套个人上下文。

2. **项目记忆不丢**
   - 架构、决策、当前状态、失败尝试按 Project 隔离，不把 A 项目记忆注入 B 项目。

3. **记忆成本可控**
   - Memory Budget 控制注入 token，Usage 展示 memory overhead，让用户知道这份记忆是否值得。

### 6.3 应该展示真实工作流

首页不应该只有口号。它应该展示用户怎么用：

```text
创建 Project
  ↓
创建 Profile，把它当成 model 名
  ↓
配置 Provider Key
  ↓
生成 remember-api API Key
  ↓
在任意客户端填写 Base URL / API Key / Model
  ↓
开始使用同一套个人 AI 记忆
```

### 6.4 应该展示“记住了什么”

首页可以放一个更有说服力的 Memory 面板：

```text
Preference
偏好 TypeScript、pnpm、简单清晰的实现。

Decision
remember-api 使用 Fastify 做 OpenAI-compatible Gateway。

Status
Web 控制台已完成 Dashboard / Profiles / Memories / Usage。

Failed Attempt
避免 Agent 套 Agent，Hermes 只作为 Memory Backend。
```

这比抽象的“AI memory”更能让用户感到：这是我的个人 AI 资产。

### 6.5 应该展示“Profile is model”

这是产品最聪明的入口设计。首页应明确告诉用户：

```text
客户端里填的 model：
remember-dev

remember-api 内部解析为：
DeepSeek + remember-api Project + 用户偏好 + 项目记忆 + Skills
```

这能立刻区分 remember-api 和普通记忆服务。

## 7. 产品价值主张

### 7.1 Functional Value：少重复解释

用户不再需要每次告诉 AI：

- 项目是什么；
- 架构怎么选的；
- 代码风格是什么；
- 上次做到哪里；
- 哪些方案不要再试。

### 7.2 Economic Value：少重新理解上下文

Memory 注入会花 token，但重新扫描仓库、重讲背景、重复试错也会花 token。remember-api 应该强调：

> 记忆不是免费，而是比重新理解更便宜。

这也是 Usage 和 Memory Overhead 的意义。

### 7.3 Emotional Value：AI 更像“我的工具”

个人 AI 的体验不是“更聪明的模型”，而是“它知道我是谁、我在做什么、我通常怎么做”。这种连续感会让用户对工具产生信任。

### 7.4 Strategic Value：上下文不被某个 Harness 锁死

AI 工具更新很快，用户可能今天用 Claude Code，明天用 Codex，后天换 Cursor。remember-api 把长期上下文放在用户自己控制的 API 后面，避免被某个客户端生态绑定。

## 8. 当前风险

### 8.1 首页表达还没有完全体现个人 AI

如果首页只说“OpenAI-compatible memory gateway”，用户会把它理解成技术中间件。应该更直接表达：

- 这是你的个人 AI 记忆层；
- 记忆属于你，不属于某个客户端；
- 换工具也延续上下文。

### 8.2 记忆质量决定成败

如果写入的 Memory 太碎、太重复、太泛化，用户会觉得它在污染上下文。后续需要加强：

- Memory 合并；
- 记忆生命周期；
- 自动摘要；
- 手动审核或批量整理；
- 过期记忆处理。

### 8.3 成本解释必须透明

记忆系统天然增加 prompt token。首页和 Usage 页都应诚实说明 memory overhead，而不是只讲“自动记忆”。

### 8.4 Project 边界必须清楚

个人 AI 可以跨工具，但不能跨项目乱记。Project 隔离是信任基础。首页和 Dashboard 都应该强调“个人偏好全局共享，项目记忆按 Project 隔离”。

### 8.5 不要做成第二个 Agent

项目文档已经反复强调避免 Agent 套 Agent。remember-api 应继续保持克制：

- 不负责执行任务；
- 不重新规划；
- 不接管 Harness；
- 只负责状态、记忆、上下文和可观测性。

## 9. 建议的首页信息结构

### 第一屏

- 标题：让你的 AI 换工具也记得你
- 副标题：个人偏好、项目记忆、Skills 和模型配置，通过一个 OpenAI-compatible API 提供给所有客户端
- 主按钮：进入控制台
- 次按钮：查看接入流程
- 右侧视觉：Profile → Context Builder → Model 的面板，而不是泛泛 dashboard

### 第二屏：为什么需要个人 AI 记忆层

用对比说明：

```text
没有 remember-api：
每个 AI 客户端各自失忆，用户反复解释项目。

有 remember-api：
客户端可以换，模型可以换，个人上下文不换。
```

### 第三屏：核心能力

- Profile is model
- Project Memory
- Editable Memory
- Memory Budget
- Usage / Cost
- Provider Adapter

### 第四屏：真实接入

展示三项配置：

```text
Base URL
API Key
Model = Profile name
```

再展示一次请求如何变成带记忆的模型上下文。

### 第五屏：控制台能做什么

不是泛泛列功能，而按用户意图组织：

- 配：Provider / Profile / API Key；
- 看：Usage / Cost / Memory Overhead；
- 改：Memory / Project / Skills。

## 10. 推荐首页主文案

### 版本 A：偏个人 AI

```text
让你的 AI 换工具也记得你

remember-api 是个人 AI 的长期记忆层。把偏好、项目状态、架构决策、失败尝试和 Skills 放进一个 OpenAI-compatible API，让 Claude Code、Codex、Cursor 共享同一套上下文。
```

### 版本 B：偏开发者工具

```text
一个属于你的 Stateful AI API

用 Profile 把 model 变成个人工作模式：绑定 Provider、Project、Memory Budget 和 Skills。任何 OpenAI 兼容客户端都能通过同一个 API 使用它。
```

### 版本 C：偏结果

```text
不用再向 AI 重讲你的项目

remember-api 会在每次请求前注入相关个人偏好和项目记忆，在请求后沉淀新的状态。换客户端、换模型，记忆仍然跟着你。
```

建议首页主标题采用版本 A，第二段补充版本 B 的技术可信度。

## 11. 结论

remember-api 最值得放大的价值，不是“管理 API Key / Provider / Usage”，这些只是控制台功能；也不是“有 Memory”，因为很多工具都会说自己有记忆。

它真正的差异化是：

> **把个人上下文从 AI 客户端里解耦出来，变成用户自己可控、可观察、可迁移的长期资产。**

因此网站首页应该少讲“网关管理后台”，多讲“个人 AI 的记忆层”；少放抽象统计，多展示 Profile 如何把一个普通 `model` 变成带偏好、项目状态和 Skills 的个人 AI。
